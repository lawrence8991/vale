## 1. Philosophy & Core Principles

### What Makes LiftKit Different

LiftKit is a **relative** design system, not an absolute one. Most design systems use:
- Fixed pixel values (`padding: 16px`)
- Static breakpoints
- Hardcoded spacing

LiftKit uses:
- **Relative units** (`em`, `rem`)
- **Golden ratio scaling** (φ = 1.618)
- **Dynamic relationships** between elements

### The Golden Ratio Foundation

Everything in LiftKit derives from φ (phi) = 1.618:
- Font sizes scale by φ
- Spacing scales by φ
- Border radii scale by φ
- Everything renders in proportion to everything else

### Optical vs Mathematical Symmetry

**Critical Insight**: Mathematical symmetry ≠ perceived symmetry.

Due to how text renders (bounding boxes include line-height whitespace), padding that is mathematically equal will *feel* unequal. LiftKit provides `opticalCorrection` props to compensate.

**The Bounding Box Problem:**
```
Text elements have a BOUNDING BOX (the full height including line-height)
and a RENDERED HEIGHT (the actual pixels of the characters).

Bounding box:    ┌──────────────────┐
                 │   (whitespace)   │  ← Line-height adds space here
Rendered text:   │   Heading Text   │  ← Actual character pixels
                 │   (whitespace)   │  ← And here
                 └──────────────────┘

When you set padding: 16px on all sides, you're measuring from the
bounding box edge, NOT the rendered text edge.
```

**Visual Comparison:**
```
MATHEMATICAL (looks wrong):     OPTICAL (looks right):
┌─────────────────────────┐    ┌─────────────────────────┐
│                         │    │                         │
│      16px padding       │    │      12px padding       │  ← LESS top
│                         │    │                         │
│   ┌─────────────────┐   │    │   ┌─────────────────┐   │
│   │  (line-height)  │   │    │   │  (line-height)  │   │
│   │  Heading Text   │   │    │   │  Heading Text   │   │
│   │  (line-height)  │   │    │   │  (line-height)  │   │
│   └─────────────────┘   │    │   └─────────────────┘   │
│                         │    │                         │
│      16px padding       │    │      16px padding       │  ← Same bottom
│                         │    │                         │
└─────────────────────────┘    └─────────────────────────┘

Result: Top looks heavy         Result: Balanced appearance
```

**The Formula:**
```
optically-corrected-top-padding = font-size / line-height

For title2 (font-size: 1.618em, line-height: 1.272):
corrected-top = 1.618em / 1.272 ≈ 1.272em

Compare to default padding of 1.618em - that's a significant reduction!
```

**Why the Eye Notices:**
The human eye naturally focuses on the **top-left** of a container first. This is where visual weight is highest, so any imbalance is most noticeable there. That's why we correct the top padding most often.

## 2. The Three Laws of Spacing

### The Fundamental Question

Consider: *How much space should go between a heading and a paragraph?*

This seems simple, but the answer reveals deep complexity:
- 1.0 units of spacing? Works.
- 1.15 units? Also works.
- 1.25 units? Still acceptable.
- 2.5 units? Now elements feel disconnected - "absurd"

There exists a **comfort zone** - a range where spacing feels "right." But once you add subheadings, images, action bars, cards with buttons... the spacing decisions multiply exponentially.

With 12 typography styles, you have **66 unique element pairings** to consider. Nobody wants to memorize 66 spacing values.

### Law 1: Every Element is Related
Every element on screen is related to every other element, even if only by virtue of being in the same viewport.

### Law 2: Some Relationships Are Stronger
Not all relationships are equal. A heading is more strongly related to its subtitle than to a navigation item.

### Law 3: Stronger Relationships = Closer Elements
Elements that are more closely related should be physically closer together.

### Practical Application

```
Relationship Strength → Spacing Size
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Strongest (same unit)  → xs, 2xs
Strong (parent-child)  → sm
Medium (siblings)      → md
Weak (different units) → lg, xl
Weakest (sections)     → 2xl, 3xl
```

### The "Larger Element Rule"
**Always apply spacing from the LARGER text element.** When spacing between a heading and body text, use the heading's spacing scale.

### The Exponential Scale
The spacing scale is **exponential**, not linear. The difference between `md` and `lg` is larger than between `sm` and `md`.

### Practical Walkthrough: The Employee Handbook

Here's how to apply the Three Laws to a real document:

**Step 1: Identify Relationships**
Look at your layout and find element pairs:
- Title + Subtitle → Strongly related (same unit)
- Heading + Subheading → Strongly related
- Subheading + Paragraph → ???

**Step 2: Ask the Relationship Question**
"Is the subtitle more related to the title above or the paragraph below?"
Answer: It's a *sub*title - belongs with the title. Use tight spacing (xs).

**Step 3: Apply the Larger Element Rule**
When spacing between elements of different sizes, derive the spacing from the **LARGER** element.
- Title (display2) + Subtitle (body) → Use display2's spacing scale
- Heading (title3) + Paragraph (body) → Use title3's spacing scale

**Step 4: Establish Hierarchy (A > B > C)**
When you have three relationships of different strengths:
```
A: Title → Subtitle     (strongest, tightest: xs)
B: Subtitle → Paragraph (medium: sm)  
C: Paragraph → New Section (weakest, widest: lg or xl)
```

**Step 5: Remember the Exponential Scale**
The jump from `md` to `lg` is LARGER than `sm` to `md`. You don't always need to skip levels - the scale handles perceived differences naturally.

**Result:** What was a chaotic document with inconsistent spacing becomes visually harmonious, with relationships immediately clear to the reader.

## 3. Golden Ratio Mathematics

### Why Relative Units? The Accessibility Problem

**The Problem with Fixed Spacing:**
```
Designer creates:     Card with 20px spacer blocks

Default browser:      Looks perfect! ✓

User with vision      Text scales up to 24px...
impairment:           But spacers stay at 20px.
                      Layout breaks. Proportions lost. ✗
```

When users change their browser's default font size (for accessibility), fixed pixel spacing doesn't scale. The result: cramped text fighting against tiny gaps, or enormous text with proportionally tiny margins.

**The Solution: Spacing Relative to Font Size**
```
Designer creates:     Card with 1.2em spacer blocks

Default browser       16px root → spacing = 19.2px
(16px):               Looks perfect! ✓

Large font setting    24px root → spacing = 28.8px
(24px):               STILL looks perfect! ✓
                      Everything scales proportionally.
```

This is why LiftKit uses `em` and `rem` units, not pixels.

### Core Constants

```css
:root {
  --lk-scalefactor: 1.618;                    /* φ (phi) */
  --lk-wholestep: 1.618;                      /* = φ */
  --lk-halfstep: 1.272;                       /* = √φ */
  --lk-quarterstep: 1.128;                    /* = ⁴√φ */
  --lk-eighthstep: 1.062;                     /* = ⁸√φ */
  
  /* Decimal versions (for subtraction operations) */
  --lk-wholestep-dec: 0.618;                  /* φ - 1 */
  --lk-halfstep-dec: 0.272;                   /* √φ - 1 */
  --lk-quarterstep-dec: 0.128;                /* ⁴√φ - 1 */
  --lk-eighthstep-dec: 0.062;                 /* ⁸√φ - 1 */
}
```

### Step Relationships

| Step Type | Multiplier | Decimal | Use Case |
|-----------|-----------|---------|----------|
| Whole | ×1.618 | 1.618 | Major scale jumps |
| Half | ×1.272 | 1.272 | Medium scale jumps |
| Quarter | ×1.128 | 1.128 | Fine adjustments |
| Eighth | ×1.062 | 1.062 | Micro adjustments |

### Formulas

**Font Size Scale:**
```
display1 = 1em × φ³         ≈ 4.236em
display2 = 1em × φ²         ≈ 2.618em  
title1   = 1em × φ × √φ     ≈ 2.058em
title2   = 1em × φ          ≈ 1.618em
title3   = 1em × √φ         ≈ 1.272em
heading  = 1em × ⁴√φ        ≈ 1.128em
body     = 1em              = 1.000em
subhead  = 1em ÷ ⁴√φ        ≈ 0.887em
callout  = 1em ÷ ⁸√φ        ≈ 0.942em
label    = 1em ÷ ⁴√φ ÷ ⁸√φ  ≈ 0.835em
caption  = 1em ÷ √φ         ≈ 0.786em
```

**Spacing Scale:**
```
4xl = 1em × φ⁵  ≈ 11.09em
3xl = 1em × φ⁴  ≈ 6.854em
2xl = 1em × φ³  ≈ 4.236em
xl  = 1em × φ²  ≈ 2.618em
lg  = 1em × φ   ≈ 1.618em
md  = 1em       = 1.000em
sm  = 1em ÷ φ   ≈ 0.618em
xs  = 1em ÷ φ²  ≈ 0.382em
2xs = 1em ÷ φ³  ≈ 0.236em
3xs = 1em ÷ φ⁴  ≈ 0.146em
```

## 7. Color System

### Color Philosophy

**Core Principle**: Color is meaningless without context.

Consider this: What does the color red mean?
- ❤️ Love (Valentine's Day)
- 🔥 Passion, energy
- ⚠️ Error, danger
- 🛑 Stop
- 🩸 Blood, violence
- 🎄 Christmas (with green)

The same red can represent love OR rage, energy OR danger. **If something can mean anything, then it means nothing at all.**

Color meaning comes from three types of context:

### 1. Literal Context (Icons & Text)
The most obvious source of meaning. When you see:
- 🔴 + ⚠️ "Error" → Clearly an error state
- 🔴 + ❌ "Delete" → Destructive action
- 🔴 + ❤️ "Favorite" → Positive action!

**Test:** Remove the color entirely. If the meaning is preserved through icons and text, your literal context is strong. Color then becomes *reinforcement*, not the sole carrier of meaning.

### 2. UI Context (Component Type)
The same color means different things on different components:

**Red on a Snackbar:**
> "Something negative **just happened**" (past tense)
> The error has already occurred.

**Red on a Button:**
> "If you click this, something negative **will happen**" (future tense)
> This is a warning about a potential action.

This is why LiftKit uses **semantic** color names:

| Traditional | LiftKit | Meaning |
|------------|---------|---------|
| `error` | `negative` | Something bad (past or future) |
| `warning` | `tentative` | Proceed with caution, uncertain |
| `success` | `affirmative` | Positive confirmation |

**Deliberate Contradictions:**
Sometimes you WANT to slow users down. A "self-destruct" dialog might use:
- 🟢 Green "Cancel" button (safe action feels "go")
- 🔴 Red "Confirm Delete" button (dangerous action feels "stop")

This contradiction creates **friction**, forcing users to actually read instead of muscle-memory clicking.

### 3. Cultural Context (Learned Associations)

> "Your design didn't fall out of a coconut tree. It exists in the context of all the other apps your users interact with."

**Traffic Lights (Universal):**
- 🔴 Red = Stop
- 🟡 Yellow = Caution
- 🟢 Green = Go

These associations are so deeply ingrained that macOS window buttons (🔴🟡🟢) don't even need icons - we just *know* red closes.

**Industry Associations:**
Quiz: Which restaurant sells fried chicken?
- App A: Red + Golden Brown color scheme
- App B: Blue + White color scheme
- App C: Green + Brown color scheme

Your brain instantly pattern-matches red + golden brown with KFC, Popeyes, Raising Cane's. This is the **"Chicken Matrix"** - color combinations trigger brand associations.

**Implication:** Your color choices position your product within a mental landscape of existing products. Choose intentionally.

### Building a Color System

**Step 1: Start with a Seed Color**
Your brand's primary color. Place it on the color wheel.

**Step 2: Find Complementary Colors**
- Rotate to find your accent color (tertiary)
- Find neutral variants for secondary
- Locate positions for red, orange, yellow, green, blue

**Step 3: Harmonization**
Raw complementary colors can clash. The algorithm adjusts saturation and lightness to ensure:
- Sufficient contrast ratios (accessibility)
- Visual harmony when used together
- Readability of text on colored backgrounds

**Step 4: Generate Tonal Palettes**
Each of your 9 key colors (primary, secondary, tertiary, error, warning, success, info, neutral, neutral-variant) splits into a tonal palette:
- 10-15 shades from light to dark
- Includes "container" variants (muted backgrounds)
- Includes "on-color" variants (text colors)

**Step 5: Sort into Light/Dark Schemes**
The algorithm selects appropriate tones for each scheme:
- Light scheme: Dark text on light backgrounds
- Dark scheme: Light text on dark backgrounds

**Result:** From one seed color → Complete design system color tokens

**Button CSS Formulas:**
```css
[data-lk-component="button"] {
  --button-font-size: var(--body-font-size);
  --button-line-height: var(--lk-halfstep);
  --button-padX: var(--button-font-size);                                    /* 1em */
  --button-padY: calc(var(--button-font-size) * (var(--lk-halfstep) / var(--lk-size-xl-unitless)));
  --button-padX-sideWithIcon: calc(var(--button-font-size) / var(--lk-wholestep));  /* Reduced when icon present */
  --button-gap: calc(var(--button-padY) / var(--lk-eighthstep));
```

**Why Asymmetric Button Padding?**
```
Button icons create an optical illusion of extra padding on the icon side,
even when padding is mathematically equal. LiftKit compensates:

Standard padding:          With icon (compensated):
┌──────────────────────┐   ┌──────────────────────┐
│  1em  [Button]  1em  │   │ 0.62em [→] [Button] 1em │
└──────────────────────┘   └──────────────────────┘
                           ↑ Reduced on icon side
```

**Button Comparison (LiftKit vs Others):**
When you draw a bounding circle around button content:
- **LiftKit**: Content fits snugly within the circle
- **iOS/Material**: Extra dead space around content

This "tightness" is what creates the satisfying, polished feel.

## 12. Decision Trees

### Choosing Spacing Size

```
What is the relationship between elements?
│
├─ Same logical unit (title + subtitle)?
│  └─ Use: xs or 2xs
│
├─ Parent-child (heading + content)?
│  └─ Use: sm
│
├─ Siblings in same container?
│  └─ Use: md
│
├─ Different functional groups?
│  └─ Use: lg or xl
│
└─ Separate sections?
   └─ Use: 2xl, 3xl, or 4xl
```

### Choosing Typography Class

```
What is the content?
│
├─ Hero/landing page headline?
│  └─ display1 or display1-bold
│
├─ Major page section title?
│  └─ display2 or display2-bold
│
├─ Section heading?
│  └─ title1, title2, or title3 (+ bold)
│
├─ Component/card heading?
│  └─ heading or heading-bold
│
├─ Main body text?
│  └─ body
│
├─ Supporting/secondary text?
│  └─ subheading or callout
│
├─ Form labels?
│  └─ label or label-bold
│
├─ Metadata/timestamps?
│  └─ caption
│
└─ Category labels/tags?
   └─ capline (uppercase)
```

### Choosing Card scaleFactor

```
What is the largest text in the card?
│
├─ display1 or display2?
│  └─ scaleFactor="display1" or "display2"
│
├─ title1, title2, title3?
│  └─ scaleFactor="title1", "title2", or "title3"
│
├─ heading?
│  └─ scaleFactor="heading"
│
├─ body (most common)?
│  └─ scaleFactor="body" (default)
│
└─ Smaller text (caption, label)?
   └─ scaleFactor="caption" or "label"
```

### Choosing Button Variant

```
What action does the button perform?
│
├─ Primary/main action?
│  └─ variant="fill" (default)
│
├─ Secondary/alternative action?
│  └─ variant="outline"
│
├─ Tertiary/subtle action?
│  └─ variant="text"
│
├─ Destructive action?
│  └─ variant="fill" color="error"
│     or variant="outline" color="error"
│
└─ In a card/tight space?
   └─ Consider size="sm"
```

### When to Use Optical Correction

```
Is there visible whitespace imbalance?
│
├─ Top of card feels "too padded"?
│  └─ opticalCorrection="top"
│
├─ Both top and bottom?
│  └─ opticalCorrection="y"
│
├─ Left/right sides feel off?
│  └─ opticalCorrection="x"
│
├─ All sides need adjustment?
│  └─ opticalCorrection="all"
│
└─ Looks fine as-is?
   └─ opticalCorrection="none" (default)
```

## Quick Reference Card

### Spacing Multipliers
```
4xl = φ⁵ ≈ 11.09    3xl = φ⁴ ≈ 6.85     2xl = φ³ ≈ 4.24
xl  = φ² ≈ 2.62     lg  = φ  ≈ 1.62     md  = 1
sm  = 1/φ ≈ 0.62    xs  = 1/φ² ≈ 0.38   2xs = 1/φ³ ≈ 0.24
```

### Typography Sizes (at 16px root)
```
display1 ≈ 68px    display2 ≈ 42px    title1 ≈ 33px
title2   ≈ 26px    title3   ≈ 20px    heading ≈ 18px
body     = 16px    subhead  ≈ 14px    caption ≈ 13px
```

### Key Formulas
```
Button padY = fontSize × (halfstep / xl)
Button padX-with-icon = fontSize / wholestep
Card padding = largest-child-font-size
Card optical-top = fontSize / lineHeight
Icon size = 1em × halfstep (square)
```
